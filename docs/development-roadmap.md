# 開発ロードマップとブランチ運用

## 現在地

`v0.2.1`時点で、COEIROINK・VOICEVOXからの通常変換、OpenUtau用USTX出力、セリフTXT・LABを含むZIP出力を公開している。編集済みUSTXを対象にした再同期モードは、LABの特殊音素対応に制約がある試験機能として公開している。

今後は、機能を急いで増やすよりも、既存機能を安全に維持できるテスト基盤と、HANAX-Uが解決したい制作上の課題を整えることを優先する。

## 開発テーマ

### 1. テストフローの確立

通常変換と再同期モードのどちらも、公開可能な決定稿テストデータと確認手順を持つ状態にする。

- `test/`にGit管理するテストプロジェクトを置く。
- `sample/`は個人の実用サンプル・検討用素材として扱い、Git管理しない。
- COEIROINK・VOICEVOXの通常変換について、入力、プレビュー、USTX、TXT・LAB ZIP、話者マッピングの確認範囲を定義する。
- OpenUtauや音源に依存する確認と、ブラウザだけで確認できる項目を分ける。
- 入力・出力・仕様の変更時には、影響するテストデータと公開前テスト計画を更新する。

現在は、通常変換用テストプロジェクトの制定を最優先とする。要件は[通常変換テストデータ仕様](normal-conversion-test-fixtures.md)に置く。

### 2. コンセプトの深化

華さん・楠さんのペルソナと制作ジャーニーを起点に、次を継続して検討する。

- HANAX-Uが短縮したい制作工程
- 初心者に残したい分かりやすさと、上級者に提供したい自由度
- 機能を追加する際の採用基準と、意図して扱わない範囲

コンセプトは[HANAX-Uコンセプト](hanax-u-concept.md)を基準文書とする。機能案は、無料の制作環境を活かせるか、OpenUtauでの編集自由度を保てるか、動画制作とのファイル対応を改善するか、の観点で評価する。

### 3. 具体的な機能実装

現時点で、次の実装テーマは確定していない。特殊音素対応は候補として保持するが、再同期モードのテストと対応範囲の設計が整うまで保留する。

機能実装は、原則として次の順で進める。

1. 上流の仕様・対応範囲・既知の制約を文書化する。
2. テストデータと受け入れ条件を定義する。
3. 機能ブランチで実装・検証する。
4. 文書・テストが整った状態で`main`へ反映し、リリース候補とする。

## ブランチ運用

`main`は、公開済みまたは公開前テストを通過した状態を保つ。GitHub Pagesとリリースは`main`を基準にする。

まとまった作業は、目的が分かるブランチで行う。

| 作業 | ブランチ例 |
| --- | --- |
| テストデータ・テストフロー | `codex/test-normal-conversion` |
| コンセプト・設計文書 | `codex/docs-concept-roadmap` |
| 機能実装 | `codex/feature-resync-phonemes` |

軽微な誤字修正など、単独で安全に確認できる変更は`main`へ直接commitしてよい。未完成の機能、仕様の選択肢が残る作業、複数回の検証が必要な作業はブランチへ分ける。機能ブランチをpushしても、`main`を公開元とするGitHub Pagesの内容は変わらない。

## 直近の順序

1. 通常変換用のテストプロジェクト要件を確定する。
2. 決定稿の`.cink`・`.vvproj`を`test/`へ追加し、公開前テスト計画へ対応を記録する。
3. コンセプト・ペルソナ・ジャーニーを掘り下げる。
4. 次の機能候補を検討する。
